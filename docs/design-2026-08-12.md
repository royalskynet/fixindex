# fixindex 檢索引擎綜合設計（2026-08-12）

參考：fixindex 自身現況 + claude-mem（thedotmack, 90k★）+ claude-mem-lite（sdsrss, FTS5+TF-IDF 混合）+ claude-memory（itsjwill, embeddings）。

## 診斷回顧（已實測根因）

fixindex 的 `fixindex find`（→ fxsearch.py BM25）過去「建完搜不到」，查證出 4 個真實缺陷，前 3 個本次已修：

| # | 缺陷 | 根因 | 狀態 |
|---|---|---|---|
| 1 | **frontmatter 全解析失敗** | `parse_fm` 用 `if not fm: continue`，fm 永遠空 → symptoms/tags 全丟，find 喪失 3x/1.5x 加權 | ✅ 已修 (in_fm flag) |
| 2 | **舊格式檔 0 entry** | `build_entries` 只索引 `## §N` 章節；無 § 檔（82 個 old-format）→ 0 entry，find 永看不見 | ✅ 已修 (fallback 整篇 body) |
| 3 | **長駝峰熱詞失配** | `kIOGPUCommandBuffer...` 被當單一 token，query `kIOGPU` 拆成 `kiogpu` → BM25 精確比對失配 | ✅ 已修 (prefix-fuzzy) |
| 4 | **fi 建出 unbsearchable** | `fi` 不回填 `symptoms`、不包 `## §N` → 新條目 find 0 命中 | ✅ 已修 (fi 自動回填+包章節) |

## 定制對「fi 建立即 find 可搜」新契約
`fi` 建立/append 現在會：從 body `**Symptom:**` 抽 symptoms 回填 frontmatter、無 § 時自動包 `## §N`（heading 用 title）——建完即被 fxsearch 索引，不需再繞 H4。

## 成熟方案可借鏡（claude-mem-lite 最契合）

### 應採納（低成本、高增益、本地無依賴）
1. **CJK 字典優先分詞**（cjkBigrams + CJK_COMPOUNDS 字典 ~300 詞）：中文詞組整 token（`数据库`→1 token）取代噪音 bigram，大幅提升中文召回與精確度。fixindex 內容大量中英混雜 → 最需要。
2. **雙向同義詞表 SYNONYM_MAP**（中↔英、縮寫↔全文）：如 `清理`↔`clean`、`google`↔`g`。查詢時 OR 展開。解決 fixindex 中英混記的召回缺口。
3. **查詢 sanitize**：清標點/控制字元/NEAR 關鍵字，避免 FTS5/BM25 解析報錯（claude-mem 有過 NUL 中斷 sqlite C 字串的教訓）。

### 應忽略 / 延後（claude-mem-lite 自己的 audit 教訓）
- **TF-IDF 向量 arm（Chroma/embeddings）**：claude-mem-lite 已 **disable**——benchmark hybrid_over_bm25 lift≈0，但付出 compute + 維護 + drift 成本。fixindex 僅 300 條、BM25 已足夠 → **不加向量**。
- **RRF 混合檢索**：需要第二檢索器才值得；單 BM25 + 同義詞展開已達標 → 暫緩。
- **SQLite/FTS5 遷移**：fixindex 是 Markdown 純檔、人人可讀、git 可 diff。維持現形，只強化 fxsearch。FTS5 的 porter/unicode61 中文弱點正是我們用字典分詞繞過的原因，遷移 SQLite 無淨增益。
